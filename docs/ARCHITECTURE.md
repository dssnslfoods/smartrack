# สถาปัตยกรรมระบบ RAG Management System

เอกสารนี้อธิบายการออกแบบระบบตาม `SRS-RAG-001 v1.0` — ทำไมจึงออกแบบเช่นนี้ และกฎธุรกิจถูกบังคับใช้ที่จุดใด

---

## 1. ภาพรวม

```
┌──────────────────────────────────────────────────────────────┐
│  Client — PWA (Tablet 8-10" / PC / Handheld Scanner)         │
│  Vanilla JS + Service Worker (Offline: ค้นหา + แผนผัง)        │
└───────────────┬──────────────────────────────────────────────┘
                │ REST + Bearer Token (JSON)
┌───────────────▼──────────────────────────────────────────────┐
│  API Layer  (server/api/routes.js)                           │
│  · ตรวจสิทธิ์ตาม Role ก่อนเข้าถึงทุก Endpoint                  │
│  · เขียน Audit Log ทุกการกระทำที่เปลี่ยนแปลงข้อมูล             │
├──────────────────────────────────────────────────────────────┤
│  Service Layer (server/services/)   ← กฎธุรกิจทั้งหมดอยู่ที่นี่  │
│  locations · suggest · search · operations · cyclecount      │
│  · reports · labels · notify                                 │
├──────────────────────────────────────────────────────────────┤
│  Data Layer (PostgreSQL — Supabase)                          │
│  · Constraint + Trigger บังคับกฎที่ห้ามละเมิดเด็ดขาด            │
└──────────────────────────────────────────────────────────────┘
```

**หลักการออกแบบ**

1. **กฎที่ห้ามละเมิดเด็ดขาด บังคับที่ฐานข้อมูล** — 1 ตำแหน่ง = 1 พาเลท (`UNIQUE`), ประวัติแก้ไขไม่ได้ (`TRIGGER`),
   รหัสตำแหน่งไม่ซ้ำ (`UNIQUE`) เพื่อให้ต่อให้มีการเขียนข้อมูลจากช่องทางอื่น (เช่น ERP Sync) ก็ยังปลอดภัย
2. **กฎที่ต้องยืดหยุ่นได้ อยู่ที่ Service Layer** — ตรรกะแนะนำตำแหน่ง, FEFO, การถูกขวาง ปรับได้โดยไม่กระทบฐานข้อมูล
3. **ทุกการเคลื่อนไหวเป็น Transaction** — ไม่มีการอัปเดตสต็อกโดยไม่ทิ้งร่องรอย (Traceability ตาม P4)
4. **ไม่มี build step ฝั่ง Frontend** — ทีม IT ของ SME แก้ไข/ดูแลเองได้ ลดต้นทุนการบำรุงรักษาระยะยาว

## 2. Data Model

โครงสร้างตรงตาม SRS §6 โดยมีส่วนขยายที่จำเป็นต่อการใช้งานจริง

| ตาราง | หน้าที่ | ส่วนที่เพิ่มจาก SRS และเหตุผล |
|-------|--------|------------------------------|
| `zones` | โซนในคลัง | — |
| `rags` | ชั้นวาง | `aisle`, `position_in_aisle` สำหรับจัดวางบนแผนผังภาพรวม |
| `locations` | ตำแหน่งจัดเก็บ | `UNIQUE(rag_id, level, depth)` ป้องกันตำแหน่งซ้ำ |
| `skus` | สินค้า | `qty_per_pallet` (เติมค่าเริ่มต้นตอนรับเข้า), `barcode` (สแกนสินค้า), `erp_item_id` (Sync ERP) |
| `pallets` | พาเลท = หน่วยจัดเก็บ | `status = PENDING_PUTAWAY` แยกขั้น "รับเข้า" ออกจาก "จัดเก็บ" ตาม UC-02 · `MISSING` สำหรับของที่นับไม่พบ |
| `transactions` | ประวัติทุกการเคลื่อนไหว | `reversal_of` รองรับการกลับรายการ (แทนการลบซึ่งถูก Trigger ห้าม) |
| `cycle_counts` / `cycle_count_lines` | ใบนับสต็อกและผลนับรายตำแหน่ง | Workflow: COUNTING → PENDING_APPROVAL → APPROVED/REJECTED |
| `pick_orders` / `pick_order_lines` | ใบสั่งหยิบ | รองรับ UC-03 ที่เริ่มจาก Pick Order |
| `utilization_snapshots` | ค่าการใช้พื้นที่รายวัน | ทำให้กราฟแนวโน้ม (FR-06.3) เร็วและถูกต้องย้อนหลัง |
| `audit_logs` | บันทึกการกระทำของผู้ใช้ | NFR-14 — ลบ/แก้ไม่ได้เช่นกัน |
| `users` / `sessions` | ผู้ใช้และการเข้าสู่ระบบ | รหัสผ่านและ PIN เก็บเป็น scrypt hash |

**ข้อสังเกตเรื่อง FK สองทาง:** `locations.current_pallet_id` ↔ `pallets.location_id` ชี้หากันเพื่อให้ query แผนผังเร็ว
ทั้งคู่ถูกเขียนภายใน Transaction เดียวกันเสมอ (ดู `services/operations.js`) จึงไม่มีสถานะครึ่ง ๆ กลาง ๆ

## 3. กฎธุรกิจสำคัญและจุดที่บังคับใช้

| กฎ | ที่มา | บังคับที่ |
|----|------|----------|
| 1 ตำแหน่ง = 1 พาเลท | SRS §3.3 | `locations.current_pallet_id` + ตรวจใน `assertPlaceable()` |
| สร้าง RAG → สร้างรหัสตำแหน่งครบทุกช่อง | FR-01.2 | `services/locations.js → syncRagLocations()` |
| ลดขนาด RAG ได้เฉพาะเมื่อช่องที่หายไปว่าง | เพิ่มเติม | `syncRagLocations()` — โยน `LOCATION_OCCUPIED` |
| Lot No. และวันหมดอายุบังคับ (เครื่องสำอาง) | FR-02.1 | `registerInbound()` + `pallets.exp_date NOT NULL` |
| ยืนยันจัดเก็บ/หยิบต้องสแกน 2 ชั้น | FR-02.3 / FR-03.3 | UI บังคับสแกนทั้งคู่ + API ตรวจว่าพาเลทตรงกับตำแหน่ง |
| หยิบต้องเรียงตาม FEFO | FR-03.2 | `pickSequence()` เรียงลำดับ + `confirmPicking()` โยน `FEFO_VIOLATION` ถ้าไม่ระบุเหตุผล |
| ตำแหน่งที่ถูกขวางเข้าถึงไม่ได้ | SRS §3.3 (Drive-In) | `blockingLocations()` ใช้ทั้งตอนแนะนำ, ตอนวาง และตอนเตือนก่อนหยิบ |
| น้ำหนักต่อชั้นห้ามเกิน | SRS §3.3 | `assertPlaceable()` รวมน้ำหนักพาเลททั้งชั้นก่อนอนุมัติ |
| โซนต้องตรงกับประเภทสินค้า | FR-04.1 | `assertPlaceable()` โยน `ZONE_MISMATCH` — ข้ามได้เฉพาะผู้มีสิทธิ์ `override:location` พร้อมเหตุผล |
| Transaction ลบ/แก้ไม่ได้ | FR-07.1 | DB Trigger `trg_txn_no_update` / `trg_txn_no_delete` |
| ผลต่างจากการนับต้องอนุมัติก่อนปรับสต็อก | FR-07.2 | `approveCycleCount()` ต้องมีสิทธิ์ `cc:approve` (MANAGER/ADMIN) |

### ตรรกะแนะนำตำแหน่ง (FR-02.2)

คะแนนรวมจากหลายเกณฑ์ แล้วเรียงจากมากไปน้อย — โปร่งใสและปรับได้:

| เกณฑ์ | คะแนน | เหตุผล |
|-------|-------|--------|
| อยู่ในโซนที่กำหนดสำหรับสินค้า | +1000 | เกณฑ์หลักตาม SRS |
| RAG นั้นมีสินค้า SKU เดียวกันอยู่แล้ว | +400 | รวมกลุ่มสินค้าชนิดเดียวกัน ลดเวลาเดิน |
| ชั้นล่าง | +200 ลดหลั่นตามชั้น | ไม่ต้องใช้รถยก ปลอดภัยกว่า (P2) |
| ตำแหน่งลึก | +15 ต่อระดับความลึก | เก็บช่องหน้าไว้ให้หยิบง่าย |
| **ตัดทิ้ง** | ถูกขวาง / เกินน้ำหนักชั้น / เกินน้ำหนักตำแหน่ง | วางจริงไม่ได้ |

ผู้ใช้เลือกตำแหน่งอื่นเองได้เสมอ (Override) และระบบจะแสดง "เหตุผลที่แนะนำ" ทุกอันดับ เพื่อให้พนักงานเข้าใจ ไม่ใช่กล่องดำ

## 4. ความปลอดภัย (NFR-12/13/14)

- **รหัสผ่าน/PIN**: scrypt + salt เฉพาะราย ไม่เก็บค่าจริง
- **Session**: token สุ่ม 256-bit อายุ 12 ชั่วโมง เก็บฝั่ง server ยกเลิกได้ทันทีเมื่อ logout
- **RBAC**: ตรวจสิทธิ์ที่ API ทุกเส้น (ไม่พึ่ง UI) — ADMIN / MANAGER / OPERATOR / VIEWER
- **Audit Log**: บันทึกผู้ใช้ + การกระทำ + ข้อมูลที่ส่ง + IP และห้ามแก้ไขด้วย Trigger
- **การ Override ทุกครั้งต้องมีเหตุผล** และเหตุผลถูกเก็บใน Transaction (ตรวจสอบย้อนหลังได้ว่าใครข้ามกฎเพราะอะไร)

## 5. Offline Mode (NFR-11)

Service Worker แคชผลลัพธ์ของ API ที่อ่านอย่างเดียว (ค้นหา, แผนผัง, ข้อมูลหลัก) แบบ *network-first*
เมื่อเน็ตขัดข้องจะใช้ข้อมูลล่าสุดที่แคชไว้และขึ้นแถบเตือนสีส้ม — การบันทึกรายการยังต้องออนไลน์
เพื่อไม่ให้เกิดสองแหล่งความจริง (ป้องกันการวางซ้ำตำแหน่งเดียวกันจากอุปกรณ์คนละเครื่อง)

## 6. Performance (NFR-01..04)

- Index ครอบคลุมเส้นทางค้นหาหลัก (sku_code, sku_name, lot_no, exp_date, location_code, สถานะ)
- ค้นหาด้วยข้อมูลตัวอย่าง ~130 พาเลท ใช้เวลา **< 10 ms** ฝั่ง server (เป้าหมาย NFR-01 คือ < 1 วินาที)
- Utilization รายวันถูก snapshot ไว้ล่วงหน้า กราฟแนวโน้มจึงไม่ต้องคำนวณย้อนหลังทุกครั้ง
- ทุก Transaction ทำงานแบบ atomic (`BEGIN IMMEDIATE`) ป้องกัน race condition เมื่อพนักงานหลายคนทำงานพร้อมกัน

## 7. งานประจำวันอัตโนมัติ

`server/index.js → scheduleDailyJobs()` ทำงานตอนเริ่มระบบและทุกวันเวลา 07:00 น.

1. บันทึก Utilization Snapshot ของวัน
2. ล้าง Session ที่หมดอายุ
3. ส่งแจ้งเตือนสินค้าใกล้หมดอายุ — ผ่าน LINE Notify เมื่อกำหนด `RAG_LINE_TOKEN`, ไม่เช่นนั้นบันทึกลง `data/notifications.log`
